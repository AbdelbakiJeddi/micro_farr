5. Queues: passing data main/app_ipc.c:41

A queue moves copies of data between tasks, and blocks the side that has to wait.

The problem

Tasks must exchange data. The obvious tool, a global variable, fails in three ways: a reader can be preempted halfway through copying a struct (a torn read); a second write can replace a value nobody read yet (a lost update); and the reader has no way to sleep until data arrives, so it polls.

The old micro_farr firmware had the second bug: the number of cells to drive was a static set by one task and read later by another.

Build it from first principles

A ring buffer of fixed slots

A queue reserves length × item_size bytes at creation. Send copies the item into the next free slot; receive copies the oldest one out (FIFO).

Copy, not share

Because items are copied, the sender can reuse its variable at once, and sender and receiver never touch the same memory.

Two wait lists

The queue keeps a list of tasks blocked on "empty" and a list blocked on "full". A send wakes the first receiver waiting; a receive wakes the first sender waiting. That is how a queue replaces polling.

QueueHandle_t q = xQueueCreate(4, sizeof(motion_cmd_t));

motion_cmd_t cmd = { .type = MOVE_STRAIGHT, .cells = 3 };
if (xQueueSend(q, &cmd, pdMS_TO_TICKS(100)) != pdPASS) {
    /* still full after 100 ms */
}

motion_cmd_t rx;
while (xQueueReceive(q, &rx, 0) == pdTRUE) {   // 0 = don't wait
    handle(&rx);
}

Break it: a full queue

A queue has a size, so it can be full. The sender's timeout decides what happens then: 0 means "give up, the item is lost"; portMAX_DELAY means "block until there is room", which slows the producer down to the consumer's speed (back-pressure).

Here the producer is 5 times faster than the consumer. A bigger queue only delays the problem; the rates have to match.

Why these values

Why length 4? Between two motion samples (10 ms) the app sends at most a burst of two or three commands: a move, an extend, or a stop. The motion task drains all of them at every sample, so 4 slots cover the burst with one to spare.
Why 12 bytes per item? sizeof(motion_cmd_t) = type (4) + cells (2) + angle (2) + profile (4) = 12 bytes, verified with the compiler. The whole queue is 48 bytes of storage.
Why a 100 ms send timeout? 100 ms is 10 motion samples. If the queue is still full after that, the motion task is stuck: motion_client returns ESP_ERR_TIMEOUT instead of hanging the app.
Why does the motion task receive with timeout 0? It must never block on commands: its blocking point is the sensor signal. It takes whatever is waiting, then runs its control step.
To remember. A queue copies the data, so sender and receiver share nothing. Size it for the largest burst, and choose what a full queue means: wait (back-pressure), or drop and report.

Deep dive: pointers and interrupts

Queueing a pointer copies only the address: the data now has two users, and you need a rule for who frees it. Prefer small structs by value; for big buffers, queue pointers into a pool where each buffer has exactly one owner at a time.

From an interrupt use xQueueSendFromISR(q, &item, &woken), then portYIELD_FROM_ISR(woken), so the task you woke runs right after the interrupt instead of at the next tick.
