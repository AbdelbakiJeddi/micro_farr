7. Event groups and notifications main/app_ipc.h:12

Some messages carry no data, only the fact that something happened.

Build it from first principles

A word of flags

An event group is one integer whose bits are flags, plus a list of tasks waiting on it. Each waiter states its condition: which bits, any or all of them, and whether to clear them when it wakes.

Setting re-checks the waiters

Every xEventGroupSetBits walks the waiting list and wakes each task whose condition is now true. Several tasks can wait on the same bit; all of them wake.

A bit is memory

A bit stays set until someone clears it, even if nobody was waiting when it was set. That is useful (a late waiter still sees the event) and dangerous (a waiter may see an old event).

EventBits_t b = xEventGroupWaitBits(ev,
        MOVE_DONE | MOVE_FAULT,
        pdTRUE,    // clear these bits on exit
        pdFALSE,   // ANY bit, not all
        pdMS_TO_TICKS(7000));
if (b & MOVE_DONE)  { /* done */ }
else if (b == 0)    { /* timeout */ }

Break it: a stale bit

The app sent move 1, then stopped waiting (a timeout, or the operator pressed DEC). Move 1 ends later and sets MOVE_DONE with nobody listening. The app now sends move 2 and waits.

Without clearing first, the wait is satisfied by the old bit: the app believes move 2 is done while the robot is still driving, and its next command is rejected as "motion busy".

Why these values

Why at most 24 bits? With 32-bit ticks, an ESP-IDF event group holds 32 bits, but the kernel reserves the top 8 for its own control flags. micro_farr uses 4 of the 24.
Why "any", not "all"? A move ends either done or faulted, never both. Waiting for any of the two wakes the app in both cases with one call.
Why clear on exit and clear before sending? Clear-on-exit consumes the bit when someone was waiting. Clear-before-send covers the case where nobody was. Both are needed.
Why a bit for SENSOR_NEW and not a notification? Either works with one receiver. An event bit kept every inter-task channel inside app_ipc with one mechanism; a notification would be a little faster.
To remember. A bit remembers that something happened, even when nobody was listening. Clear the result bits before you start the action you are going to wait for.

Deep dive: task notifications

Every task has a built-in 32-bit notification value. xTaskNotifyGive(handle) and ulTaskNotifyTake(pdTRUE, timeout) act like a counting semaphore with no object to create, and are the fastest signal FreeRTOS has. The limit: one receiver, known by its handle.

Setting event bits from an interrupt (xEventGroupSetBitsFromISR) is deferred to the timer service task, because walking the waiting list is too long for an ISR. A notification from an ISR is immediate.
