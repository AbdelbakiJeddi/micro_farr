10. Designing a system docs/architecture.md

How micro_farr ended up with three tasks, and how to do the same for any project.

The method

  1. List the jobs with their period and deadline.
  2. Group jobs that share data and period into one task; split jobs with different deadlines.
  3. Priority follows the deadline: the shortest deadline gets the highest priority (deadline-monotonic ordering).
  4. One channel per data flow: command → queue, state → mailbox, "it happened" → event bit.
  5. One owner per resource: motors → motion task; OLED, buttons, flash → app task.
  6. Size and place: measure stack high-water marks; pin the time-critical tasks to their own core.

Why these choices

Why three tasks, not four? A separate UI task was considered. It would add two more channels, and every FSM state would be split across two tasks, to drive a screen nobody reads while the robot moves. Only one FSM state is active at a time, so the app task draws its own screen.
Why is motion above sensor, when the sensor comes first? Deadline ordering ties them (same 10 ms). The tie is broken by the data flow: motion must react the instant a sample is published, before the sensor task finishes its loop.
Why does the app poll buttons every 50 ms? UI_POLL_MS = 50: a human button press lasts about 100 ms or more, so polling every 50 ms never misses one, and the app spends almost all of its time blocked in vTaskDelay.
Why one event group for everything? Four bits in one word, one object to create and inspect. The bits never collide because each has one setter.
To remember. Tasks follow deadlines; channels follow data. Commands → queue, state → mailbox, "it happened" → event bit. One owner per resource.
