3. Scheduler: priorities and preemption main/app_config.h:42

Several tasks are ready, one CPU is free. Four rules decide who runs.

Build it from first principles

When does the scheduler run?

The scheduler is kernel code that picks the next task. It runs at two kinds of moments: on every tick interrupt, and whenever a task blocks or makes another task ready (sending to a queue, setting a bit, giving a mutex).

How does it choose?

The kernel keeps one ready list per priority. Choosing is just "take the first task of the highest non-empty list", so it costs the same with 3 tasks or 30.

The four rules that follow

  • The highest-priority Ready task runs.
  • A higher-priority task that becomes ready runs at once: preemption, no wait for the tick.
  • Equal priorities take turns at every tick: time slicing.
  • Nothing ready: the idle task (priority 0) runs.

Break it: starvation

The first rule has a dark side: a high-priority task that never blocks keeps the CPU forever. Below, the control task (priority 3) waits for the next sample either by blocking or by polling a flag in a loop.

Polling looks harmless. At priority 3 it means the sensor task (priority 2) never runs, so the flag is never set: the control task waits for itself. The idle task never runs either, and the ESP-IDF task watchdog resets the chip.

Why these values

Why a 1000 Hz tick? The tick is the unit of every timeout and delay. At 1000 Hz (CONFIG_FREERTOS_HZ=1000) the resolution is 1 ms, which the 10 ms sensor period and the 50 ms sensor-lost timeout need. The ESP-IDF default of 100 Hz would make pdMS_TO_TICKS(5) equal 0. The cost is 1000 short interrupts per second per core.
Why a 5 s watchdog? CONFIG_ESP_TASK_WDT_TIMEOUT_S=5 watches both idle tasks. Long enough for slow blocking work such as the 2 s IMU calibration (1000 samples × 2 ms, with delays between them), short enough to catch a task stuck in a loop.
Why motion 10 above sensor 9? Both run on core 1. The sensor publishes a snapshot, then signals; because motion is higher, it starts its control step the instant the signal is set, without waiting for the sensor task to reach its delay.
Does taskYIELD() fix polling? No. It only gives the CPU to another ready task of the same priority; lower tasks still never run.
To remember. A priority is a promise to block. The higher the priority, the shorter the work between two blocking calls must be.

Deep dive: time slicing and the idle task

Time slicing only matters between tasks of equal priority. micro_farr gives every task its own priority, so it never time-slices.

The idle task frees the memory of deleted tasks and feeds the task watchdog. Code that must run "when nothing else does" can hook into it, but must never block there.
