2. Tasks: create, stack, states main/tasks/sensor_task.c:90

A task is a function that never returns, plus a private stack, a priority and a state.

The problem

Page 1 said "each job gets its own stack and saved context". What does that look like in memory, and how does the RTOS know which task may run?

Build it from first principles

The task control block

For every task the kernel keeps a small record, the TCB: priority, current state, name, the core it may run on, and the saved stack pointer. The TCB is how the scheduler sees a task.

The stack holds the paused task

While a task is not running, its registers sit at the top of its own stack. Only the stack pointer is stored in the TCB, so a switch is cheap: a few dozen registers pushed and popped.

Five steps per switch

① push the running task's registers, ② store its SP in its TCB, ③ choose the next task, ④ load that task's SP, ⑤ pop its registers. The CPU continues inside the other task as if it had never left.

The four states

The state field of the TCB answers "may this task run now?"

  • Running: on a core right now (one per core).
  • Ready: wants the CPU, waits for a higher-priority task to stop.
  • Blocked: waits for time, data or an event. Costs no CPU at all.
  • Suspended: paused by hand with vTaskSuspend(). Rarely needed.

The key move is Running → Blocked. A task that never blocks never gives the CPU to anything below it.

Minimal code

static void sensor_task(void *arg)
{
    TickType_t last_wake = xTaskGetTickCount();
    while (1) {                          // never return
        read_and_publish();
        vTaskDelayUntil(&last_wake,
                        pdMS_TO_TICKS(10));  // Blocked
    }
}

xTaskCreatePinnedToCore(sensor_task, "sensor",
                        4096,  // stack, BYTES on ESP-IDF
                        NULL,  // argument
                        9,     // priority, higher = more urgent
                        NULL,  // handle (optional)
                        1);    // core
Why 4096 bytes for sensor and motion? A round size with margin over what their loops use. The real check is uxTaskGetStackHighWaterMark(NULL) after the worst case: it returns the smallest free space ever left.
Why 8192 bytes for the app task? The speed-run planner keeps its search arrays on the stack: 256 B of parents, 1024 B of directions, 512 B of BFS queue, 256 B of visited flags, about 2 KB, plus snprintf buffers for the OLED. The 787-byte maze is static, kept off every stack.
Why priorities 10, 9 and 3, and not 24? ESP-IDF allows 0–24. Its own service tasks sit high: the esp_timer task at 22, the inter-core IPC tasks at 24. Keeping application tasks well below lets those services preempt us when they must. Only the order of our priorities matters, not the gaps.
To remember. A task = function + stack + TCB. It must reach a blocking call in every loop pass: blocking is what hands the CPU to everyone below it.

Deep dive: bytes, overflow, the end of a task

Bytes, not words. Vanilla FreeRTOS counts stack depth in words of 4 bytes. ESP-IDF counts in bytes. Code copied from a FreeRTOS tutorial gets 4× less stack on ESP-IDF.

Overflow. ESP-IDF detects most overflows and panics with A stack overflow in task … has been detected. Silent corruption is still possible with large local arrays: measure the high-water mark.

Never return. Returning from a task function aborts the program on ESP-IDF. A task that has finished calls vTaskDelete(NULL).
