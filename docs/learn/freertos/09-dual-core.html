9. Dual core on the ESP32-S3 main/app_config.h:40

Two cores run FreeRTOS at the same time. Tasks can now run truly in parallel.

Build it from first principles

Two schedulers, one memory

The ESP32-S3 has two cores sharing the same RAM. ESP-IDF FreeRTOS runs the scheduler on both (SMP, symmetric multiprocessing): each core picks the highest-priority ready task it is allowed to run.

Affinity

A task created with a core number is pinned: only that core runs it. With tskNO_AFFINITY either core may. Pinning gives predictable timing: you know exactly which tasks compete on a core.

Why interrupts-off is no longer enough

On one core, turning interrupts off stops every other task. On two cores, the other core keeps running. A critical section therefore also needs a spinlock: a flag set with an atomic compare-and-set instruction, which the other core spins on until it is released.

static portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

portENTER_CRITICAL(&mux);  // interrupts off here, other core spins
shared_counter++;          // a few instructions only
portEXIT_CRITICAL(&mux);

Why these values

Why sensor and motion on core 1? They form the control loop: sample, then control step, every 10 ms. On their own core, nothing slow (OLED, planning, flash) can ever be ready in front of them, so their timing depends only on each other.
Why the app on core 0? app_main() already runs there (CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0), and Wi-Fi/Bluetooth would too if used. Slow, human-speed work belongs together.
Why save the maze only at the goal? Writing flash disables the flash cache, which pauses code running from flash on both cores for the length of the write. At the goal the robot is stopped, so a pause of the control loop costs nothing.
Why keep spinlock sections tiny? While one core holds the lock, the other core may be spinning, doing no work at all, with its interrupts off.
To remember. Pin time-critical work to one core and keep slow work on the other. On two cores, a critical section needs a spinlock (portMUX_TYPE), and parallel access is real, not just interleaved.

Deep dive: what pinning does not protect

Pinning separates CPU time, not data. The motion task (core 1) and the app (core 0) can peek the snapshot mailbox at the same instant. That is safe only because a FreeRTOS queue protects itself with its own spinlock.
