8. Shared data: races, mutexes, inversion main/params.c:35

Preemption can stop a task between any two instructions. Shared data has to survive that.

Build it from first principles

count++ is three instructions

On the ESP32-S3 (Xtensa), count++ on a global compiles to a load, an add and a store:

l32i a8, a9, 0 ; read count into a register addi a8, a8, 1 ; add 1 s32i a8, a9, 0 ; write it back

An interrupt, and so a task switch, can happen between any two of them. If another task changes count in that gap, its change is overwritten: a race condition.

Critical section

The fix is to make the three steps indivisible for other tasks: a critical section. A mutex (mutual exclusion lock) does that between tasks: take it before, give it after; a task that finds it taken blocks until it is free.

SemaphoreHandle_t lock = xSemaphoreCreateMutex();

xSemaphoreTake(lock, portMAX_DELAY);
count++;               // keep this as short as possible
xSemaphoreGive(lock);

Break it: priority inversion

A lock brings a new problem. Low takes the lock; High needs it and blocks. Then Medium, which never touches the lock, wakes and preempts Low. High now waits for Medium, a task less urgent than itself, for as long as Medium runs.

A FreeRTOS mutex fixes this with priority inheritance: while High waits, Low temporarily runs at High's priority, so Medium cannot preempt it. A binary semaphore has no owner, so it cannot do this: never use one as a lock.

Why these values

Why do the tuned gains need no lock? params has one writer (the app, when you press INC/DEC) and one reader (motion). Each value is an aligned 32-bit float, and an aligned 32-bit store is a single instruction on the ESP32-S3: a reader sees either the old or the new value, never half of each. This holds only for independent values; a group that must change together would need a lock.
Why does the OLED need no lock? Only the app task ever calls the OLED and button code. One owner means no sharing, so nothing to protect.
And the I2C bus, shared by sensor and app? The ESP-IDF I2C master driver serializes transactions on a bus with its own internal lock, so the ToF, IMU and OLED transfers never interleave.
To remember. Best: don't share. Give each resource one owner task and send it messages. Otherwise use a mutex (not a binary semaphore), and hold it as briefly as possible.

Deep dive: Mars Pathfinder, deadlock, ISRs

In 1997 the Mars Pathfinder lander kept rebooting on Mars. A high-priority bus task waited on a mutex held by a low-priority task while medium-priority tasks ran: priority inversion. A watchdog saw the bus task miss its deadline and reset the system. The fix, uploaded from Earth, was to turn on priority inheritance for that mutex.

Deadlock: task A holds lock 1 and waits for lock 2 while task B holds lock 2 and waits for lock 1. Neither ever runs again. Rule: take locks in the same order everywhere.

Never take a mutex inside an interrupt: an ISR cannot block.
