1. Why an RTOS main/main.c:74

One slow job can make a fast job late. A scheduler fixes that by interrupting the slow job.

The problem

A micromouse runs three kinds of jobs at very different speeds. Each job has a period (how often it must run), a cost (how long it takes) and a deadline (when it must be finished).

The OLED is the trap: its cost is longer than the sensor period.

Build it from first principles

Step 1: one CPU, one instruction at a time

A core executes one instruction stream. "Doing three jobs" means interleaving them: the only question is where you are allowed to switch.

Step 2: the super-loop switches only between jobs

A while (1) loop runs each job to the end, then the next. A new sample that arrives mid-OLED waits for the whole pass:

worst reaction R = C_sensor + C_control + C_oled = 2 + 1 + 25 = 28 ms > 10 ms deadline

Step 3: switch in the middle of a job

To react faster, the CPU must be able to stop the OLED code anywhere. A hardware interrupt can do that. The RTOS then saves the registers of the stopped job (its context) and loads another job's registers. That is preemption.

Step 4: every job needs its own stack

A stopped job still has local variables and return addresses in flight. They must stay intact until it resumes, so each job gets a private stack. Function + stack + saved context + priority = a task.

Step 5: the urgent job no longer depends on the slow one

R_control = C_control + switch time ≈ 1 ms + a few µs

The OLED still takes 25 ms of CPU, but it now runs in the gaps.

Super-loop
void app_main(void)
{
    while (1) {
        read_sensors();      // 2 ms
        control();           // 1 ms
        if (oled_due())
            oled_draw();     // 25 ms
        wait_next_10ms();
    }
}

Break it

Same three jobs, 60 ms of CPU time, one cell per millisecond. The OLED wants a redraw at 3 ms and 33 ms.

In the super-loop, each oled_draw() hides the next two samples. With tasks, the sample at 10 ms arrives while the OLED draws: the scheduler stops the OLED task, runs sensor and control, then lets the OLED finish later.

Why these values

Why does the OLED take 23 ms? A full frame is 128 × 64 pixels / 8 = 1024 bytes. On I2C every byte costs 9 clock bits (8 data + 1 acknowledge). At 400 kHz: 1024 × 9 / 400 000 = 23.04 ms, before any protocol overhead. A faster bus would shrink it, not remove it.
Why sample at 100 Hz? At 450 mm/s the robot moves 4.5 mm per sample, fine enough for the wheel speed loops. Faster would load the I2C bus that also carries the IMU, three ToF sensors and the OLED.
Why redraw only at 10 Hz? One frame holds the shared I2C bus for 23 ms. At 10 Hz that is 23 % of the bus time; at 20 Hz it would be 46 %, and every ToF and IMU read would wait behind it more often.
Is the 10 ms deadline real? Yes: the next sample overwrites the previous one. A control step that runs late either uses stale data or is skipped.
To remember. A super-loop reacts no faster than its longest job. An RTOS always runs the most urgent task that is ready, and preempts anything less urgent.
In micro_farr. main/main.c:74-76 starts three tasks: sensor, motion, app. main/app_config.h:39-48 holds their rates, cores, priorities and stacks. The OLED lives in the lowest-priority task, and draw_status() in main/app/state_explore.c throttles it to 10 Hz.
Deep dive: could a super-loop do this too?

Yes, by hand: cut oled_draw() into 8 page writes of 3 ms and send one per pass. That is cooperative multitasking: you must chop every slow job yourself, and one forgotten long call breaks the timing again.

An RTOS chops for you. The price: one stack per task (RAM), a few microseconds per switch, and data shared between tasks that can be read half-updated (page 8).

On ESP-IDF there is no bare super-loop anyway: app_main() already runs inside a FreeRTOS task called main (core 0, 3584-byte stack in this project's sdkconfig).
